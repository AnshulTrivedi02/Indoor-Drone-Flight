## 1. XUKO (ruling 4): the port now writes the FMT records; and a FINDING about XUKO's clock in Replay

### 1.1 What changed (`~/ardupilot_ukf`, two commits, Replay-only code paths)
- **`e88aa34a3d`, the FMT emission:**
  - In Replay, `AP_Logger_Backend::ensure_format_emitted()` returns true unconditionally ("we trust that Replay will
    correctly emit formats"), and nothing did. So every dynamically named record (`WriteStreaming`: XUKF, XUKO, XUKS,
    XUKH, XUKT and the FGO's XFG*) went out with no FMT.
  - `AP_Logger::WriteV` now calls `Safe_Write_Emit_FMT(f)` under `APM_BUILD_TYPE(APM_BUILD_Replay)` before the first
    record of each type. It emits FMT + FMTU once per type.
  - `Write_Emit_FMT` keeps its Replay id window [220, 230]; dynamic ids count down from 230. The df_reader check
    (0 undeclared types) is what proves no type fell outside it.
  - Non-Replay builds (the flying port, boards) already emit FMTs on first use, and are unchanged.
- **The same commit adds the U10 G3 counters** (§2): `NavUKF::n_chol_retry()`/`n_chol_fail()` getters and
  `write_end_stats()`. At the end of the log, Replay prints `thesis shadow UKF: end of run: n_chol_retry=N
  n_chol_fail=M` and writes a NEW file `ukf_stats.csv`. The four existing CSVs are untouched.
- **`0a214d29d3`, the XUKO stamp (FINDING, below):** in Replay, XUKO is stamped `AP::dal().micros64()`. That is the
  replayed frame's logged RFRH time, the same clock `NavEKF3::Log_Write` stamps XKF1 with (`AP_NavEKF3_Logging.cpp:371`).
  Non-Replay builds keep `AP_HAL::micros64()`.

### 1.2 FINDING: every replayed XUKO so far was on the Replay PROCESS clock
- XUKO was stamped `AP_HAL::micros64()`. On the vehicle that is the FC time. **In Replay it is the Replay process's
  own clock:**
  - on `cl_a_tex_half` (a 270 s flight), XUKO TimeUS ran 0.025 s … 3.14 s;
  - it differed on every run: the ONLY bytes that differ between the old be7c4d18 log and the FMT-only build's log are
    XUKO TimeUS bytes 3–5 (6 673 records).
- **The port spec's assumption was wrong in Replay.** §S2 said "TimeUS is the same `AP_HAL::micros64()` stamp as
  `XUKO` (the current time)". That holds only on the vehicle.
- It also explains part of the old fork-flown interleave (d17_v2): the replayed XUKO were not even on the log clock.
- **With the FMT alone, the scorer's UKF row would have errored** on `cl_a_tex_half` ("only 0 estimator samples inside
  the window"; `eval/results/xuko_fmt/score_cl_a_tex_half_FMTonly_scratchbab0b427.json`). On a log whose window
  overlapped the process clock it could have returned a meaningless number. So the FMT-only build was NOT installed.
- **After the fix**, XUKO TimeUS spans 5.50–272.38 s, inside XKF1@0's 4.09–272.39 s. XUKF (the horizon state,
  stamped at its own time) interpolated at the XUKO stamps agrees with XUKO to a median of 2.3 mm and a p99 of 5.1 mm
  horizontal (max 2.16 m at a single instant; not investigated). A wrong clock would put the two metres apart
  throughout.
- **No criterion changes,** but the user must see this before any real log is scored against the signed-off prereg:
  XUKO in Replay now means "the current-time output at the replayed frame's time". Onboard it is stamped at the write
  (HAL time). The two differ by at most one loop.

## 4. H10 (ruling 8): the pilot-takeover guard in `fly_trial.py`, tested

### 4.1 The code
- **The bench rule, ported exactly** (`realflight/sitl_bench/flight_script.py --h10-guard`): no LAND when the FC is in
  STABILIZE (0), ALT_HOLD (2) or LAND (9). The FC mode is read PASSIVELY from the FC's own latest HEARTBEAT
  (pymavlink's per-system state, GCS heartbeats ignored), with no extra receive.
- **Plus a latch, where the real hazard was:**
  - `land()` waits 180 s wall for the disarm, then raises `TrialFailure`;
  - the D24 failure path in `main()` then calls `land()` again, i.e. it re-commands LAND under a pilot who took
    ALT_HOLD;
  - now, once a pilot mode is seen after a LAND (the script's or the watcher's), no further LAND or mode command is
    sent, and the script only watches for the disarm.
- `run_trial.sh`: a `FLY_TRIAL` override (unset = the main checkout's `fly_trial.py`, unchanged). It was needed
  because `run_trial.sh` hard-codes `$HOME/thesis_ws/fly_trial.py`.

### 4.2 Offline mock test (default behaviour unchanged)
`tools/test_fly_trial_h10.py` → `eval/results/h10/mock_test_2026-10-12.json`, ALL PASS. It drives the OLD
(`HEAD:fly_trial.py`) and the NEW `main()` against the same fake FC and fake clock, and compares every sent command with
its arguments and time:
- **6 default scenarios, commands IDENTICAL:**
  - a normal trial;
  - a normal trial with GCS heartbeats interleaved;
  - WatcherLost in GUIDED;
  - a TrialFailure in GUIDED (position outage);
  - GROUND_TEST;
  - a slow disarm inside the cap.
- **2 declared differences** (the bench rule's "already in LAND"): when the FC is already in LAND (stuck LAND, or
  the watcher's LAND then watcher loss), OLD sends a redundant LAND and NEW does not. Everything else is identical.
- **4 takeover scenarios:**
  - ALT_HOLD or STABILIZE after the script's LAND, held past the cap;
  - B10b(1): ALT_HOLD, then watcher loss;
  - ALT_HOLD after the watcher's LAND.
  - In all four, OLD sends a LAND after the takeover and NEW sends no LAND or mode command. Everything before the
    takeover is identical.
- In the two watcher scenarios, NEW still sends cruise velocity setpoints (17 and 5) between the takeover and the
  moment it notices the watcher loss. A pilot mode ignores them, and they are not mode changes (reported, not
  failed).
