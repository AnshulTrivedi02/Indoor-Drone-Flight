## The linearisation-point definition (exact, as implemented)

Nodes `V_0..V_n` (n = `room_ukf_replay.py`'s `rts_nodes`):

- **`V_0`** = the state fed into the **first** `predict_rts` call after the re-anchor (i.e.
  `room_ukf_replay.py`'s own `xa[0]`, raw). **Not** simply "immediately after re-anchor": any
  range/flow/tag update landing between the re-anchor event and that first predict runs through
  the ordinary forward code path like any other update (bag event timing, not controlled), so
  `V_0` already bakes those in. Such updates are therefore **not recorded as ops** — there is
  nothing to re-linearise; they sit inside the fixed `V_0`, never iterated (`chain_started` guard
  in `room_ukf_ipls_replay.py`). `V_0` is fixed for every iteration, exactly as `ukf_core.rts_smooth`
  already never reads `D[0]`/`Pp[0]` for the stored forward pass.
- **`V_{k+1}`** = the filtered state after predict step `k` and every measurement update that
  follows it, up to (not including) the next predict — i.e. `room_ukf_replay.py`'s `XA[k]`.
- **Predict step `k`** (maps `V_k` → `V_{k+1}`'s prior) is linearised by unscented SLR about the
  iteration-(j−1) smoothed marginal of `V_k` — the state the predict step actually reads.
- **Every measurement update belonging to node `k+1`** (range, each flow axis, each tag
  component — pseudo-yaw never occurs post-anchor in experiment T, see below) is linearised
  about the iteration-(j−1) smoothed marginal of `V_{k+1}` — the state the update conditions.
  All measurements at one node therefore share **one** reference point: there is exactly one
  smoothed marginal per node (`room_ukf_replay.py` records none between e.g. the flow_x and
  flow_y sub-updates of the same node), so none was invented. This is a documented simplification
  of "every measurement update … about the smoothed marginal at that step" down to "about that
  step's node" — it does **not** reproduce the forward UKF's own intra-node sequential
  re-linearisation, and that is why iteration 0 is **not** built from this machinery (next point).
- **Iteration 0 is a bypass**: `ukf_core.rts_smooth` called directly on the recorded forward-pass
  arrays (`XA`, `PA`, `XP`, `PP`, `DD` — identical construction to `room_ukf_replay.py`). This
  reproduces the stored `ukf_rts.tum` bitwise *by construction* (same function, same inputs),
  which is also why the per-node (not per-sub-step) reference above is harmless: it only ever
  applies from iteration 1 on, where IPLS is already an approximation, not an identity.
- **Frozen inputs** (never recomputed from an iterated state, in any iteration): predict's
  `da`/`dv`/`dt`; flow's `omega_body` — the UKF's own bias-corrected gyro average, `om`, exactly
  as the forward pass computed it (this is the UKF's own model: the bias enters `om` at the
  mean, outside the sigma points, so freezing it is consistent with the model, not a separate
  choice); flow/range/tag values after `GroundProximityFlow.replace`; every gated accept/reject
  decision (a rejected scalar never appears in any iteration's op list — no re-gating, ever).
- **Pseudo-yaw / tag-yaw pivot**: both are linearised as `h(x) = wrap(x[8] - ref_m[8])` — pivot
  = the SLR reference's own yaw (self-referential, matching `ukf_core.update_yaw_pseudo`/
  `update_heading`'s own "relative to the current mean" convention), **not** a value frozen from
  the forward pass. Tag-yaw's frozen absolute reading gives target `wrap(psi - pivot)`;
  pseudo-yaw's target is `0` exactly (a zero-innovation regulariser, not evidence — see
  `update_yaw_pseudo`'s own docstring on EKF3's matching mechanism). In Experiment T the
  pseudo-yaw update only ever fires **before** the re-anchor (the forward pass's own condition
  is `not anchored`), so it never actually appears in any recorded op in this experiment —
  confirmed empirically on `T_A_r1`: `pseudo_yaw_fired_before_anchor` = 8, and 0 pseudo-yaw ops
  appear in `batch_ops` (the forward-pass `chain_started` guard makes this structural, not just
  observed).

## Gate results

### G3 (synthetic, `test_ipls_g3.py`)

- **G3(a) linear-Gaussian: PASS.** `U._process` is exactly linear when `da == 0` (roll/pitch/yaw
  and both bias blocks pass through unchanged; `R` stays fixed since `_rotvec_to_R(0) == I`
  exactly, so p/v are an exact linear map of the previous p/v/accel-bias). `U.h_range` is already
  exactly linear. Iteration 0 (the bypass) is therefore already the exact Gaussian smoother, and
  iteration 1 reproduced it to **max abs diff 4.99e-10** (spec: ≤ 1e-9), with
  `max_change_m` at iteration 1 = **5.93e-10** (spec: ≤ 1e-9, i.e. converges within one iteration).
- **G3(b) short nonlinear toy: FAIL, as written, not redesigned.** Real `U._process` (genuine
  constant body rates → rotation) and `U.h_flow` + `U.h_range`, noiseless targets from a true
  trajectory, 8 predict steps, fixed before running.
  - **First run had a test-harness bug** (found and fixed, in the harness only, not the toy):
    `_fwd_arrays` replayed a `flow_x` op and a `flow_y` op as two *separate*
    `U.update_flow(...)` calls, each padding the other axis with a fake `0.0` — but
    `update_flow` always fuses both axes per call, so this fused a bogus zero-flow measurement
    on the untouched axis every time. That inflated the pre-fix iteration-0 cost to **16226.86**,
    with the full pre-fix trace `[16226.86, 0.0345, 0.4473, 0.4435, 0.4435, 0.4435]` (6 entries,
    `tol_m=1e-6`). Fixed by grouping adjacent `flow_x`/`flow_y` ops from the same message into
    one `update_flow([zx, zy], ...)` call, matching the real replay.
  - **Post-fix trace (`tol_m=1e-6`, the value fixed before this run — see note below):
    `[1.3510, 0.4420, 0.4435]`** — a cost **increase of 0.0015** between iteration 1 and
    iteration 2, at the step where the maximum horizontal position change was **1.9e-8 m**
    (i.e. the trajectory had already converged to within nanometres; the cost nonetheless
    ticked up). **This is reported as the gate result: FAIL.**
  - I initially (incorrectly) re-ran this check with `tol_m` loosened to the pre-registered 1 mm
    stopping tolerance, under which the toy stops after iteration 1 with `[1.351, 0.442]` — no
    increase observed, because iteration 2 (where the tiny increase occurs) is never reached. On
    review this was **rejected as an improper post-hoc redesign** (changing a parameter after
    seeing the failure, which the pre-registration's "fix the toy before running, no re-design
    after seeing the result" rule forbids just as much as changing the cost definition would).
    `tol_m=1e-6` was restored and **that is the result of record**: **G3(b) FAILS.**
  - **Diagnosis, not an excuse**: the sign and location of the increase (tiny, right as the
    trajectory stops moving by any practical measure) is consistent with IPLS's own fixed point
    not being the literal MAP point of the cost this module evaluates — unscented SLR propagates
    `E[f(x)]`, not `f(E[x])`, so a converged IPLS run can sit at a MAP cost above the true
    minimum (here ~0.4435, against the true generating trajectory's MAP cost of exactly 0, by
    construction). This is a real, reportable property, not something this stage is empowered to
    fix by redefining the cost.

## Open issues / ambiguities for the pre-registration owner to rule on

1. **Which cost.** The module currently evaluates the MAP objective at the smoothed means with
   the *exact nonlinear* `f`/`h` (pre-registration: "sum of squared whitened residuals", which
   does not say against which point). IPLS's own fixed point is not generally the MAP point (see
   G3(b) diagnosis above). An alternative — the whitened residuals of each iteration's own
   *linearised* model (the `H`/`A`, `Qtot`/`Rtot` IPLS's forward/backward recursion is actually
   consistent with) — might behave differently (e.g. be guaranteed non-increasing, as ordinary
   Gauss–Newton is on its own linearised subproblem). Not implemented; flagged, not resolved.
2. **What "across iterations" means for the stopping-coupled cost check.** Iterations actually
   taken under the pre-registered 1 mm stopping rule, or iterations in general (i.e. does the
   gate apply only up to and including the iteration that triggers convergence, or to however far
   the run is pushed)? This stage used "however far run" (matching the literal gate text, and
   because loosening it after seeing a failure was rejected as improper) — but the owner may rule
   differently.
3. **The per-node (not per-individual-update) linearisation reference for j≥1**, documented above
   and in `ukf_ipls.py`'s module docstring, is a genuine simplification this stage made (no finer
   grained smoothed marginal exists in the recorded chain) rather than something the
   pre-registration specifies exactly. It does not affect iteration 0 (exact by construction).
