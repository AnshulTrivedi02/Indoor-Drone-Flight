## Design notes / judgement calls

- **Shared check pool for C02/C03** (`save(..., pool="C0203")`): `allowed_for(fid)` filters `CHK` by exact fid, so
  C02's chart and C03's table draw numbers from one shared pool of data-identity checks (`ROW3`, `REF3`, `VREF`,
  the per-group diverged/collapsed counts) registered once under `"C0203"`, rather than duplicating every check
  twice. `guard()`/`save()` take an explicit `pool=` override for this.
- **Number guard extended to captions and tables, not just drawn figure text** (advisor-suggested, not in the
  existing restyle scripts): `guard(fid, text)` applies the same NUMTOK stray-number check to caption bodies and
  markdown table cells as `save()` applies to on-canvas text. This caught several real gaps during the build (room
  geometry numbers mentioned only in prose, band values like the 1.10 in P-E3b.1, the registered-id self-references)
  that would otherwise have been uncross-checked numbers sitting in a caption or table file.
- **`_strip()` fix for composite "fake numbers" in identifiers**: registered-hypothesis ids (`P-E3.5a`, `H-E2.1`,
  `P-E3b.1`) and this group's own candidate ids (`C02`, `C03_table.md`) contain digit sequences that `NUMTOK` would
  otherwise demand a check for (e.g. the `3.5` inside `P-E3.5a`). Stripped before scanning via `ID_RE`/`CAND_RE`,
  the same fix the restyle generators already apply to `EKF3` (-> `EKF`, so its `3` isn't mistaken for a claimed
  value). Genuine claim numbers (the `1.5` in "<= 1.5 x lap-1", the `1.10` in P-E3b.1's band) are untouched by this
  and still require their own passing check.
- **C04's registered-verdict table is a markdown table candidate, not a chart** (brief: "verdicts belong in
  tables, not on figures"). Its own `.md` file legitimately carries PASS/FAIL words, the same convention as
  `TA_verdicts.md`/A1-A3; only its **caption** file (`captions/C04.md`) stays D113-clean (no verdict words, ends in
  the pointer line) -- the caption describes the table, the table itself carries the verdicts.
- **C04 flags the P-E3b.1 (1%) "SATISFIED, flagged" qualification** (found in advisor review): 6 of its 9 passing
  runs have no matched plain-arm run to compute a ratio against (it diverged), per the 2026-10-23 user ruling
  recorded in `e3_results.md` and TA row 73. Added as a `note` column on that row rather than silently dropping the
  qualification the source register carries.
- **C05/C06 pointer is `none (descriptive)`, not `H-E3.1`** (corrected in advisor review): each panel is ONE run,
  while H-E3.1 is scored over the 9-run population, and C05's left panel is Experiment 3 (no wrong IDs at all), not
  an Extension E3 run. Pointing at H-E3.1 would have been exactly the kind of over-claim the restyle handover

### Defect fixed: C02's diverged-run markers overlapped (and two related defects found on a zoomed re-check)

**Symptom (the one named in the brief)**: in the "1% wrong IDs, FGO as built (plain)" column, 6 of the 9 runs
diverged and were drawn as "x" markers at the shared categorical "diverged" row (`YDIV`). All six were assigned
x-positions from the same 9-point `linspace(j - 0.32, j + 0.32, 9)` used for the live (finished) runs in that
column, so the six diverged positions (indices 1, 2, 4, 5, 7, 8 of that linspace) had gaps as small as 0.08 data
units, visibly smaller than the marker width at this figure's scale, so several "x" marks rendered on top of
each other and were not individually distinguishable.

**First-pass fix** gave live and diverged runs their own independent linspans instead of sharing index slots, and
was committed (`804880f`) on the strength of viewing the full-size PNG, before a pre-hand-back review pass. **That
full-size review was not thorough enough.** A second look (zoomed crops of the dense columns, the near-zero band
and the left spine, not just the full-size image) found three more things the full-size view had hidden:

1. **The live squares in dense 9-run columns still overlapped each other** -- the same defect class as the named
   one, just with squares instead of "x" marks. "5% wrong IDs, FGO as built" has all 9 runs within 0.18 m of each
   other (4.04-4.22 m) and rendered as one contiguous blob at the original `linspace(j - 0.32, j + 0.32, 9)`/`ms=6`
   sizing.
2. **The lowest live squares sat on the x-axis spine.** The "no wrong IDs" column (0.0484-0.0760 m) and the
   lowest "1% wrong IDs, robust FGO" point (0.0496 m) are close enough to zero that, with `ax.set_ylim(0, ...)`,
   the marker's own half-height crossed the spine line.
3. **The "diverged" row was not actually visually separated from the numeric range**, despite the coordinator's
   explicit ruling that this needs checking ("make sure it is"). The original fix kept it as a sixth y-tick
   (`[0, 1, 2, 3, 4, YDIV]`) on the same continuous spine with the same gridline style as the numeric ticks, with
   a gap (5.2 - 4.22 = 0.98) not much bigger than the regular 1.0 tick spacing -- at a glance it read as a sixth

**Second-pass fix** (`eval/figs_cand_c.py`, the whole C02 block rewritten):

- **A genuine broken y-axis**, not a tick on a shared scale: two stacked `Axes` from one `GridSpec` (`height_ratios
  =[1, 5]`, `hspace=0.12`), sharing x. The top `Axes` (`axd`) holds only the categorical "diverged" row (its own

- **Live markers get a wider span and a smaller marker**: `linspace(j - 0.42, j + 0.42, n_live)` (was `+-0.32`) at

### Defect fixed: C05/C06's tag-map squares were opaque-filled, hiding the diamonds and each other's outlines

**Symptom**: the "FGO final tag map" squares in `e3_maps()` were drawn with `mfc=SURF`. `SURF` is
`thesis_style.py`'s page-background white (`"#ffffff"`, used for `figure.facecolor`/`axes.facecolor`), not a
transparent fill -- so each square was an opaque white rectangle with an orange outline, not an open/hollow
marker. This mattered in two places: in C05 panel (a) (no wrong IDs, map matches the truth) every square sat
exactly on its true-tag diamond and hid it underneath the opaque fill; in C05 panel (b) and C06 panel (a) (the
two "collapsed" plain-FGO runs, where several of the 8 estimated tags land within centimetres of each other) the
later-drawn squares' opaque fill covered the earlier squares' outlines, so individual estimates in the cluster
were not all individually traceable. A first pass at fixing this (see below) wrongly asserted the squares were
"already hollow" and that the diamonds "stayed visible through the overlap" -- false as built; both claims are
retracted and the fix was actually made, not just re-described.

**The coincident positions themselves are not a defect** -- `stats.json`'s `landmarks_final` for those two runs
genuinely places several of the 8 estimated tags within centimetres of each other, which is exactly what "the
final map is shrunk inward" / "the final map folded into a different arrangement" (the C05/C06 captions' own
wording) describes: the wrong-ID runs' optimiser converged several distinct tags onto nearly the same point.
Jittering the plotted positions to separate them would misrepresent the estimate, so the positions are unchanged.

**Fix** (`eval/figs_cand_c.py`, `e3_maps()` and its legend handle): `mfc=SURF` -> `mfc="none"` on both the
plotted landmark markers (line ~549) and the "FGO final tag map" legend entry (line ~561), so the squares are
genuinely open outlines with a transparent interior. Re-rendered and viewed (plus zoomed crops of C05 panel (a),
C05 panel (b) and C06 panel (a)): every true-tag diamond in C05 (a) is now visible inside its square, and every
square's outline in both collapsed clusters is traceable even where several overlap, confirming the "open =
hindsight" convention the captions already claimed. C01, C02 and C07 (which don't use `e3_maps()`) are unaffected
-- confirmed byte-identical PNGs against the prior commit.
